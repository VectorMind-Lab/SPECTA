Important scope fact discovered by this audit: NOTHING outside
lib/core/extensions/ imports the extension manager, runtime, verifier, manifest
parser or registry. The only link from the app's reachable graph into that
folder is the three Drift table classes imported by specta_database.dart.
Consequently the extension runtime code is not reachable from lib/main.dart and
Dart's front-end drops it from the built kernel: probing the APK's
kernel_blob.bin finds the table names (extension_versions, trust_level, ...) but
finds neither "specta_request" nor "SpectaExtension". This also explains why the
APK is byte-for-byte the same size across three builds made from different
extension source.

Consequence for evidence: the debug APK proves the Android/Gradle configuration
and the schema, and it does NOT exercise the Phase 1 runtime code. That code is
covered only by the unit suite. Recording that distinction is the point of this
section.

3. GENUINE DEFECTS FOUND AND FIXED
================================================================

--- Defect 1: DriftExtensionRegistry.uninstall violated its own foreign key ---

File: lib/core/extensions/manager/drift_extension_registry.dart

Root cause: uninstall deleted the `extensions` parent row first, then the
`extension_versions` and `extension_failure_logs` rows. Both child tables
declare REFERENCES extensions(id) with no ON DELETE action, and
specta_database.dart enables PRAGMA foreign_keys. SQLite therefore aborted the
parent delete:

  SqliteException(787): FOREIGN KEY constraint failed, constraint failed

Effect: uninstalling any extension that had a rollback version or a recorded
failure threw instead of uninstalling. ExtensionManager.uninstall and
rollback-adjacent flows would surface that failure to the caller. Nothing in the
Phase 1 suite caught it, because every test used InMemoryExtensionRegistry,
which has no constraints.

Fix: delete children first, inside one transaction so the three deletes are
atomic.

Evidence: the new Drift registry suite reproduces the exception before the fix
("uninstall removes the extension, its versions and its failures [E]") and
passes after it. The same suite also proves PRAGMA foreign_keys really is
enforced (a failure row for a non-existent extension is rejected).

--- Defect 2: every manager failure was attributed to extension id "import" ---

File: lib/core/extensions/manager/extension_manager.dart

Root cause: the private _buildFailure helper hard-coded extensionId: 'import'.
Every ExtensionFailure returned by loadRuntime and callOperation therefore
carried the wrong identity: loading a disabled extension, loading a missing
extension, or calling an operation on an unloaded runtime all reported
extensionId 'import'.

Effect: ExtensionFailure.extensionId is the field diagnostics are keyed on
(and toDiagnostics() is the structured record). Misattributing it makes
per-extension health reporting and failure correlation wrong.

Fix: _buildFailure now requires the caller's extension id. Call sites pass the
real id, or ExtensionManager.unidentifiedExtension ('<unidentified>') for the
one case where no id is known yet (source file could not be read).

Evidence: reverting only this change makes the new tests fail with
"Expected: 'com.example.absent'  Actual: 'import'".

--- Defect 3: non-JS sandbox failures escaped loadExtension ---

File: lib/core/extensions/runtime/extension_runtime.dart

Root cause: the two steps that evaluate the extension code caught only
`on JsEvalException`. The ExtensionJsSandbox contract allows any Dart exception
out of a native JS engine (FFI errors, platform errors). Anything that was not a
JsEvalException propagated out of ExtensionRuntime.loadExtension, out of
ExtensionManager.loadRuntime, and into the caller.

Effect: this breaks the phase's stated invariant that a failing extension never
takes SPECTA down with it, and it is the exact failure mode the runtime exists to
prevent.

Fix: both steps now catch Object and convert to a controlled ExtensionFailure.
Timing out during load() is additionally classified as ExtensionFailureType
.timeout rather than a generic runtime error.

Evidence: reverting only this change makes the new test fail with an uncaught
"Bad state: native engine failure" thrown from the test body at
extension_runtime.dart:112.

--- Defect 4: a failed load leaked a live JS engine ---

Files: lib/core/extensions/runtime/extension_runtime.dart,
       lib/core/extensions/manager/extension_manager.dart

Root cause: ExtensionRuntime.shutdown() began with `if (!_loaded) return;`, so a
runtime whose extension code never loaded could never dispose its sandbox. The
manager builds the runtime (and therefore the sandbox, which owns a QuickJS
context) before calling loadExtension, and on failure returned Err without ever
shutting it down. Nothing else held a reference.

Effect: each failed load leaked a JS engine for the process lifetime.

Fix: shutdown() always calls dispose() (it still runs the extension's shutdown()
only when loaded); the manager shuts the runtime down on the failure path.

Evidence: the new test "shutdown disposes the sandbox even when nothing was
loaded" fails (Expected: true, Actual: false) when the early return is restored.

--- Defect 5: a host request failure produced an unhandled error ---

File: lib/core/extensions/runtime/extension_runtime.dart (_onRequest)

Root cause: the try/catch only covered decoding the extension's payload. The
`_api.request(...).then(...)` chain was outside it, so an exception from the
host's ExtensionRuntimeApi.request implementation rejected the returned future
instead of producing the structured error object that the same method already
returns for a malformed payload.

Fix: _onRequest is now async with a single try covering decode, dispatch and
encode; any failure yields the structured
{status: null, ok: false, headers: {}, body: null, json: null, latency: 0,
error: ...} payload.

--- Hardening applied with Defect 3 ---

load() had no timeout, unlike every other operation. The sandbox factory also
creates the sandbox before the first evaluate, so an extension whose load()
never settles would hang the load indefinitely. It now uses
.timeout(defaultOperationTimeout), the same 30 s policy the operation path
already declared.

--- Code comments corrected: claims the implementation did not support ---

These are documentation-of-code fixes, not behaviour changes. The previous
comments overclaimed enforcement, which is exactly what makes a security
boundary untrustworthy.

  * runtime_api.dart (ExtensionRequest): said SPECTA "enforces timeouts, method
    restrictions, and headers". It does not: the runtime transports whatever
    URL, method and headers the extension asks for. The comment now states that
    scheme/method/header policy belongs to the concrete ExtensionRuntimeApi
    implementation, which does not exist yet.
  * runtime_api.dart (ExtensionRuntimeApi): now says these are the capabilities
    SPECTA exposes, that this is a restricted API surface rather than an
    OS-level sandbox, and that no CPU/memory ceiling is applied.
  * flutter_js_sandbox.dart: replaced the generic "Security boundary" list with
    what is actually enforced (verified against flutter_js 0.8.7) and an
    explicit "What this does NOT provide" section.
  * extension_runtime.dart (sandboxBootstrap): dropped the claim that no network
    is reachable (request() is the network path) and recorded the contract fact
    that the runtime instantiates a class literally named `Extension`.

7. SECURITY AUDIT - WHAT IS AND IS NOT ENFORCED
================================================================

Prompted by the brief's rule: do not claim a boundary merely because the
documentation asserts it.

Architecture as implemented:

  ExtensionManager -> ExtensionRuntime -> ExtensionJsSandbox (abstract)
                                        -> FlutterJsSandbox (flutter_js)

What IS enforced today (each verified in source or against the package):

  1. No network primitive in the engine. flutter_js only wires fetch/XHR when
     the host calls enableFetch() (lib/extensions/fetch.dart) or asks for
     getJavascriptRuntime(xhr: true). SPECTA calls neither, and grep confirms
     enableFetch appears only in comments.
  2. Two bridge channels, no more. ExtensionRuntime registers exactly
     `specta_request` and `specta_log` via sandbox.onMessage. A message on any
     other channel has no handler and is dropped (tested).
  3. No native bindings registered. The runtime is created as a bare
     QuickJsRuntime2 with a stack size; no module handler, no filesystem, DOM,
     process or platform object is injected.
  4. Host-side file reads are performed by Dart, not JavaScript. The manager
     reads the .js file itself; nothing exposes a file API to the engine.
  5. Failures are contained. Every sandbox exception on the load path and the
     operation path becomes a controlled ExtensionFailure (defect 3 fixed).

What is NOT enforced, and must not be claimed:

  a. This is not an OS-level sandbox. Extension JavaScript executes inside the
     SPECTA process. The boundary is the absence of bindings, not isolation.
  b. No CPU or memory ceiling. QuickJsRuntime2 accepts `timeout` and
     `memoryLimit`, and this build sets neither. Their precise semantics were
     not verified here, so enabling them was deliberately NOT done. The only
     guard is the Dart-side Future.timeout in ExtensionRuntime, which cannot
     interrupt a synchronous CPU-bound JavaScript loop - a runaway `while(true)`
     in an extension is not currently stopped by anything.
  c. No request policy. There is no URL-scheme allow-list, no method
     restriction and no header filtering. _onRequest forwards whatever the
     extension sends. ExtensionRuntimeApi has no concrete implementation in
     Phase 1 - it is an interface, so no policy can exist yet. This is the main
     reason "controlled extension APIs" is PENDING rather than PASS.
  d. Declared capabilities are not enforced. ExtensionCapabilities and
     CapabilityFailure are modelled, but the runtime calls
     _spectaInstance.search(...) etc. regardless of what the extension declared.
     Nothing in the manager ever reads a declaration before an operation. The
     "capabilities must be declared explicitly" statement in PROJECT_STATE
     describes intent, not current behaviour.
  e. No health-state model. The brief's Healthy / Degraded / Temporarily
     unavailable / Disabled by user / Incompatible vocabulary is not
     implemented. What exists is: an `enabled` flag, a failure log with a
     retryable flag, and healthCheck(). Usefully, the code does NOT implement
     the "disable after three failures" rule that appears in the earlier
     reasoning document - the brief forbids it and the code correctly omits it.

Verified in the repository: no private key material of any kind (.pem, .jks,
.keystore, base64 "PRIVATE KEY") exists anywhere in the project. Only the public
key is present, in lib/core/extensions/verification/trusted_keys.dart.

8. ED25519 TRUST MODEL - WHAT IS FROZEN AND WHAT IS NOT
================================================================

The primitive is real and the public key is present. The complete signing
protocol is NOT frozen, and this section records that rather than inventing one.

What is verified:
  * SignatureVerifier uses cryptography's Ed25519 against the trusted public
    key, and rejects null/empty/malformed signatures, signatures from another
    key pair, and a tampered message.
  * decodeSignature enforces the `ed25519:BASE64` shape and a 64-byte payload.
  * Valid -> TrustLevel.official; missing/invalid -> TrustLevel.unverified, as
    the brief's table specifies.
  * The private signing key is absent from the repository.

What is NOT verified, and cannot be from here:
  * No test proves a positive result. TrustLevel.official is never produced by
    the suite, because producing it needs the private key, which is deliberately
    kept off-repo. A test that merely calls the verifier with invented values
    would not be evidence of correctness, so none was added.

Protocol questions that are undefined, quoted from the code as it stands:
  1. The signed payload is manifest.toSignedContent() - canonical JSON of
     apiVersion, author, id, name, type, version and any present
     description/language/icon/website. It does NOT cover the extension's
     JavaScript body. A valid signature can therefore be attached to modified
     code; the signature authenticates metadata, not the executable content.
     Whether that is the intended protocol is a product decision, not something
     this audit may decide.
  2. The payload is passed as String.codeUnits, i.e. UTF-16 code units, not
     UTF-8 bytes. For any non-ASCII metadata the bytes to sign differ depending
     on the encoding convention; the signing side must agree with the verifier.
  3. Adding or removing an optional manifest field changes the signed payload,
     so re-signing is required whenever optional metadata is edited.
  4. There is no signing tool, no key rotation path and no revocation story in
     the repository.

Until items 1-4 are agreed, "the extension trust protocol" is a working
primitive plus a provisional payload definition. It should be frozen before any
signing tool or extension catalogue is built on top of it.

9. KGP / GRADLE STATUS
================================================================

The question the previous note left open was whether the JVM-target mismatch was
actually fixed and whether the remaining warning is the same problem. They are
two different things, and the first one is genuinely fixed.

  1. Original Java/Kotlin JVM target mismatch: FIXED, with evidence.
     - android/gradle.properties no longer suppresses validation
       (kotlin.jvm.target.validation.mode is absent).
     - android/build.gradle.kts aligns Kotlin to JvmTarget.JVM_17 for
       subprojects applying either 'kotlin-android' or
       'org.jetbrains.kotlin.android', and sets Java 17 for com.android.library.
     - Bytecode was inspected directly (class-file major version):
         build/app                        -> major 61 (Java 17)
         build/cryptography_flutter       -> major 61 (Java 17)
         build/flutter_js                 -> major 61 (Java 17)
         build/package_info_plus          -> major 61 (Java 17)
         build/wakelock_plus              -> major 61 (Java 17)
         build/jni, build/jni_flutter     -> major 55 (Java 11)
         build/media_kit_*                -> major 52 (Java 8)
       The two plugins that previously failed validation now compile to Java 17.
       The modules still at 8/11 do not apply KGP, and they keep their own
       compileOptions because a module's own build script overrides the
       subprojects block.
     - Decisive point: the build now succeeds with Kotlin's strict JVM-target
       validation ENABLED. If any Kotlin module disagreed with its Java target,
       the build would fail. It does not.
     - The Java 8 "source/target value 8 is obsolete" javac warnings present in
       the earlier apk_build.log no longer appear.

  2. Remaining KGP warning: NOT the same problem, NOT resolved, NOT suppressed.
     Flutter reports:
       WARNING: Your app uses the following plugins that apply Kotlin Gradle
       Plugin (KGP): cryptography_flutter, flutter_js
     Cause: cryptography_flutter 2.3.4 and flutter_js 0.8.7 both apply the
     Kotlin Android plugin themselves, which Flutter's move to Built-in Kotlin
     is deprecating. Flutter states future versions will fail to build for apps
     using such plugins.
  3. Can it be fixed safely inside Phase 1? No. It requires either upgrading
     both plugins to Built-in-Kotlin-compatible releases or replacing them.
     Neither is available in the pinned baseline, and both changes are
     dependency/architecture decisions the brief forbids making silently.
     Recorded as a deferred upstream limitation. Nothing was suppressed to hide
     it - specifically, kotlin.jvm.target.validation.mode was NOT re-added.

  4. Two undocumented Gradle settings exist and were left alone:
     android.newDsl=false and android.builtInKotlin=false, both marked as
     added by the Flutter template. android.builtInKotlin=false is why the
     plugins' KGP application still matters on this toolchain.
     kotlin.incremental=false is set deliberately, with the reason recorded in
     the file (the project path contains a space, "SPECTA APK", which has
     corrupted Kotlin incremental caches).
