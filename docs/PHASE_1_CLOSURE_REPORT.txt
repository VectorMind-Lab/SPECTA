3. THE FROZEN SIGNING PROTOCOL (v1)
--------------------------------------------------------------------------------

Identifier : SPECTA-EXT-SIG-V1
Scheme     : ed25519
Status     : FROZEN. Changing any byte of this definition invalidates every
             existing signature, which is the reason it is pinned by tests.

3.1  THE EXACT SIGNED BYTES

The signed payload is the concatenation, as UTF-8 bytes, of exactly five parts:

    "SPECTA-EXT-SIG-V1"  LF
    <decimal byte length of the metadata part>  LF
    <metadata part bytes>
    <decimal byte length of the body part>  LF
    <body part bytes>

  * No other bytes are added. The protocol appends no trailing newline, no
    terminator and no padding.
  * The two length prefixes are decimal ASCII with no leading zeros and no sign.
  * LF is a single 0x0A byte. It is a protocol delimiter, so the count of
    delimiters cannot depend on the host platform's line endings.
  * The length prefixes exist so the metadata/body boundary is part of the
    signed data. Without them, swapping bytes across the boundary would produce
    the same payload.

3.2  THE METADATA PART

  * Compact JSON: no whitespace between tokens.
  * Object keys sorted ascending by code unit.
  * Encoded as UTF-8. It is NOT String.codeUnits / UTF-16. This is
    load-bearing: for a non-ASCII author name the two encodings differ, and the
    audit found the earlier implementation using code units.
  * Fields included, in canonical order:
      apiVersion, author, capabilities, description, icon, id, lang, name,
      type, version, website
  * `capabilities` is included, rendered by ExtensionCapability.encodeDeclaration
    as the sorted, comma-joined capability codes. An extension therefore cannot
    widen its own permissions and keep a valid signature.
  * Fields omitted: `signature` (a signature cannot sign itself) and any field
    that is absent, null or an empty string.
  * Field names in the payload are the contract names above, not the manifest
    `@field` spellings (`lang`, not `@lang`).

3.3  THE BODY PART

  * The extension's JavaScript body: everything after the header's closing
    `// ==/SpectaExtension==` line, verbatim, including its own line endings.
  * The body IS covered. Signing metadata without the executable code would let
    anyone replace the code while keeping the signature, which is precisely the
    attack the protocol exists to prevent.
  * Body extraction is deterministic and independent of the header: editing a
    header field changes the metadata part only.

3.4  MANIFEST AND SIGNATURE ENCODING

  * Manifest field:      `// @signature ed25519:<base64>`
  * Signature bytes:     raw Ed25519, 64 bytes, standard base64 (with padding)
  * Public key:          raw 32 bytes, base64, in
                         lib/core/extensions/verification/trusted_keys.dart
  * `SignatureVerifier.decodeSignature` requires exactly the two-part form
    `ed25519:<base64>` producing exactly 64 bytes; anything else is rejected.

3.5  VERIFICATION PROCEDURE

    1. Parse the header; extract `@signature`.
    2. Rebuild the payload exactly as in 3.1 from the parsed manifest and the
       body of the file being imported.
    3. Ed25519-verify the payload against the published public key.
    4. Valid  -> TrustLevel.official
       Missing, malformed, wrong-key, or any change to the signed bytes
              -> TrustLevel.unverified
    5. Import never rejects on trust. Trust is data a later policy layer acts
       on; classification is not enforcement.

3.6  DETERMINISM AND EXTERNAL REPRODUCIBILITY

  * Ed25519 signing is deterministic for a given key and message, so a signing
    tool reproduces byte-identical signatures. Pinned by a test.
  * As independent evidence that the written definition is sufficient, the
    payload for the closure probe below was ALSO rebuilt from this document by a
    separate implementation (Python) and matched the Dart bytes exactly:
    same 367-byte length, same magic, same 193/148 length prefixes, same
    SHA-256.

4. CAPABILITY POLICY (implemented and enforced)
--------------------------------------------------------------------------------

4.1  VOCABULARY — closed, and deliberately short

     network   the controlled host `request()` channel
     logging   the controlled host `log()` channel
     search    the `search(query, page)` contract operation
     latest    the `latest(page)` contract operation
     details   the `details(url)` contract operation
     sources   the `getSources(reference)` / `refreshSource(reference)` ops

  There is no filesystem, contacts, SMS, photo, device-identifier, database,
  native-code or application-control capability, and none may be added without
  an explicit product decision. No Android permission is created for an
  extension.

4.2  DECLARATION

  * Manifest field: `// @capabilities network,search`
  * Parsed at import; whitespace and case are tolerated.
  * An unrecognised token REJECTS the manifest rather than being dropped. A
    silently narrowed declaration would leave an extension appearing to hold
    permissions it was never granted, and the rejection is the correct side to
    fail on.
  * Absence is the default: an extension that declares nothing gets nothing.
  * The declaration is part of the signed payload, so capabilities cannot be
    escalated without invalidating the signature (proved by test).

4.3  ENFORCEMENT POINTS

  * Contract operations: `ExtensionRuntime._callOperation` refuses an operation
    whose capability was not declared, before any JavaScript is evaluated, and
    returns a structured CapabilityFailure (type CAPABILITY_ERROR, the name of
    the missing capability, the extension id, not retryable).
  * `request()` channel: `_onRequest` checks `network` FIRST, before parsing the
    payload, so an undeclared capability is not reachable by sending something
    the parser chokes on. Refusal is a structured error object returned to
    JavaScript, not an exception.
  * `log()` channel: `_onLog` drops messages when `logging` is undeclared. Logging
    has no host side effect, so a silent no-op is the correct refusal and the
    message never reaches the host sink.
  * `capabilities()` and `healthCheck()` are deliberately NOT gated: gating
    capability discovery would make the contract unreachable, and gating liveness
    probing would make a failing extension indistinguishable from a forbidden one.

4.4  EVIDENCE

  Disabling the gate (`isGranted` forced to true) makes 9 tests fail, including
  every denial test and the request/log channel tests. The enforcement is real,
  not decorative.

5. REQUEST POLICY (the controlled request boundary)
--------------------------------------------------------------------------------

The audit found the concrete request policy missing: the runtime forwarded
whatever an extension asked for. It is now an explicit, injectable value object.

  Schemes          https, http. file/ftp/data/javascript/content/blob/ws/wss
                   refused. `file:` matters most: it would expose the
                   filesystem through the ordinary URL parser.
  Methods          GET, POST, HEAD. DELETE/PUT/PATCH/TRACE/CONNECT refused.
  URL length       2048 characters
  Request body     64 KiB
  Response body    8 MiB, enforced by aborting the transfer rather than
                   buffering it
  Redirects        5
  Timeout          default 15 s; a requested timeout is CLAMPED to 60 s, not
                   refused
  Credentials      URLs carrying user:password@ are refused
  Order            scheme is evaluated BEFORE host, so file:///etc/passwd is
                   reported as SCHEME_NOT_ALLOWED rather than as a malformed URL.
                   A blank URL is INVALID_URL, not NOT_ABSOLUTE.

Structured outcomes: the API never throws. It always returns an ExtensionResponse
with ok=false and a canonical ExtensionFailureType (NETWORK_ERROR, TIMEOUT,
HTTP_ERROR, INVALID_RESULT, UNSUPPORTED, RUNTIME_ERROR). Denials are counted
separately from dispatched requests (`deniedCount` vs `requestCount`).

Logging: method, scheme and host only. The full URL is never logged, because
extension URLs routinely embed tokens and signing parameters. Verified by test.

Scope, stated plainly: this is a transport policy. It contains no provider
logic and implements no anti-bot, authentication, paywall or DRM bypass.

Transport: `DartIoHttpTransport` on dart:io HttpClient. NO NEW DEPENDENCY was
added; dart:io is already available on every target SPECTA builds for.

Covered by the real engine: initialise and evaluate; a minimal extension loading

`request()` path reaching a host transport; malformed JavaScript failing as a
controlled failure; a runtime exception becoming a failed result; shutdown
disposal; repeated load/shutdown; and a failed load cleaning up.

How the environment gap was closed for automation
  * On Windows, flutter_js loads `quickjs_c_bridge.dll`, which ships inside the
    pub cache at flutter_js-<version>/windows/shared but is only found on the
    process loader path. `tool/run_tests_real_js.sh` puts it there.
  * Running the suite through that script makes all 9 execute and pass.
  * Running `flutter test` without it SKIPS the group with a printed reason.
    Skipped is reported as skipped and is never reported as passing.

Three REAL defects were exposed by executing the engine, none of which a fake
sandbox could reveal:
  1. The engine delivers an already-JSON-decoded payload to message handlers,
     while the handler assumed a String. Every `request()` and `log()` from real
     JavaScript failed before reaching the host.
  2. QuickJS rejects top-level `await` in script mode, so loading an extension
     could never succeed on the real engine.
  3. A closed QuickJS runtime cannot be reopened, so a second load on the same
     sandbox silently failed.

7. RUNTIME LIMIT FINDINGS (measured against the shipped engine)
--------------------------------------------------------------------------------

Probed directly against flutter_js 0.8.7 / QuickJS on this machine:

  memoryLimit   `QuickJsRuntime2(memoryLimit: n)` does NOT apply a limit. The
                bundled bridge does not export `jsSetMemoryLimit`; the option is
                accepted and ignored. NOT ENFORCED.

  timeout       `QuickJsRuntime2(timeout: n)` does NOT interrupt a synchronous
                runaway loop: `while (true) {}` ran past the timeout and had to
                be killed. It also mis-fires on `await`-driven code, aborting
                promises that were still progressing. NOT RELIABLE.

  Consequently this build sets neither option. The only limit that exists is the
  Dart-side `Future.timeout` in ExtensionRuntime, which bounds awaited operations
  but CANNOT interrupt synchronous CPU-bound JavaScript.

  What this means: a buggy or malicious extension can occupy the Dart isolate
  until its script finishes. Budgeting CPU time would require either
  platform-level isolation or a bridge that supports interrupting evaluation.
  This is a KNOWN LIMITATION of Phase 1, not a solved problem.

SECURITY MODEL — accurate statement

  The SPECTA JS runtime is a RESTRICTED-API IN-PROCESS RUNTIME BOUNDARY.
  It is NOT an OS sandbox, NOT a process boundary, and NOT resource-safe.

  What it does enforce: no native bindings are registered (no DOM, no
  filesystem, no process, no platform objects); the engine's own `enableFetch()`
  is not used, so there is no unmediated engine-level network path; a global
  `fetch()` IS defined by the host shim, but it is a thin front for the same
  controlled `request()` channel and passes the same `network` capability gate and
  the same ExtensionRequestPolicy checks (scheme allow-list, private/loopback host
  blocking, redirect rules, body limits). See SOURCE_RUN_REPORT.md 14.1; only
  two host channels exist (`specta_request`,
  `specta_log`); declared capabilities are checked on every operation and every
  channel call; and every evaluation is wrapped so a JS exception never crashes
  the host.

  What it does NOT enforce: process isolation, CPU-time limits, memory limits,
  and any protection against an extension that simply spins.

10. FAILURE ISOLATION (preserved and extended)
--------------------------------------------------------------------------------

  * JS errors are contained: a JS exception becomes an Err result.
  * Non-JsEvalException failures from the native engine are also contained.
  * Host request failures become a structured error payload, never an unhandled
    exception or an unhelpful promise rejection.
  * A failed load disposes its sandbox instead of leaking a live JS engine.
  * shutdown() always disposes, even for a runtime that never loaded.
  * Failure attribution uses the real extension id. A load/call failure used to
    be recorded against the literal id 'import'; it now carries the actual id.
  * Failures raised before a manifest is parsed use the documented sentinel
    ExtensionManager.unidentifiedExtension ('<unidentified>'), and never a real
    extension id.
  * No global catch was added that would hide diagnostics.

11. HEALTH MODEL
--------------------------------------------------------------------------------

An explicit, minimal model now exists (lib/core/extensions/identity/extension_health.dart),
because the agreed design needs a vocabulary for "which source/extension should
be preferred" without inventing ranking.

  States       healthy, degraded, temporarily_unavailable, disabled, incompatible
  Precedence   incompatible > disabled > recent-failure count
  Thresholds   degraded at 2 recent failures; temporarily unavailable at 3
  Window       24 hours
  API           ExtensionHealthRules.evaluate(...) is a pure function

DELIBERATELY NOT IMPLEMENTED: automatic disable-after-N-failures, and any smart
source ranking. Classification is descriptive only and mutates nothing: an
extension with 10 recent failures stays enabled and installed, and still appears
in the enabled list. Choosing among sources is a later-phase decision that this
model prepares for; it does not make it.

17. KNOWN LIMITATIONS (carried forward honestly)
--------------------------------------------------------------------------------

  1. No CPU-time or memory ceiling for extension JavaScript. Measured, not
     assumed (section 7). A runaway script can occupy the isolate.
  2. The runtime is not an OS-level sandbox (section 7).
  3. Real device / emulator verification remains PENDING (section 18).
  4. The KGP warning from cryptography_flutter and flutter_js persists; fixing it
     needs upstream releases, not a Phase 1 change.
  5. The production private key is stored in a non-standard PEM format that
     standard tools reject (section 3.7). Recorded, not fixed.
  6. Redirects are followed up to the policy limit without re-evaluating the
     scheme allow-list against the redirect target. dart:io only follows
     HTTP(S) redirects and the initial URL was checked; stated rather than
     implied.
  7. Response bodies that are not valid UTF-8 are returned as a lossy Latin-1
     projection. Extensions needing raw bytes cannot currently be served.
  8. Trust classification is data, not enforcement: an unverified extension still
     installs and is enabled. A later policy layer must decide what to do with
     unverified extensions.
